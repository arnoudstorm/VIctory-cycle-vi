# Laptop rounds 19-23: merged single exe, the 3 GB regression, three builds

Hardware: Ryzen 7 8840HS, Radeon 780M (UMA), 16 GB (15.3 GB visible). Workload: the title
started by `victory.exe play` (the double-click path), Series S, DLSS off, guarded by
`work/benchmark-safe.ps1` (stop below 0.5 GB available RAM, or above 14 GB private).
Metric used for comparisons: private memory and GPU shared memory 20 s after start (title
screen), because run length depends on how much RAM other apps hold (start free varied
6.4-10.8 GB between runs). No run in this report reached the world, so FPS, frame times
and rendering correctness in the world were not measurable; the title screen runs at
~110-120 fps in all builds.

The GDKX archive in Downloads was not used (provenance could not be verified, no licence).

## Task 2: buffer windows over unmapped pages

Not measurable yet. The earlier census put windows outside buffers at 2 MB at the title
screen and 1.1-1.9 GB only in the world, so the window opportunity does **not** overlap the
title-screen regression (the savings would add). "1,357 MB over unmapped pages" is the size
of windows that contain *some* unmapped page, not the unmapped bytes. Constraints found for
a safe reduction: windows are CPU-filled (`shared_buffer`, memcpy), so reserved (tiled)
resources cannot back them directly; shrinking windows risks GPU page faults because root
views are not bounds-checked. Needs a world run to measure before any change.

## What still stops the laptop

After the title screen C still grows from ~6.6 to 8-9 GB private and to 2-3.7 GB GPU shared
within a minute (pipeline translation: ~2,500 shaders and ~2,200 host pipelines in the first
35 s; texture re-uploads), against ~10 GB available with the usual apps open. The guard's
figure is Windows' available memory (it includes the standby cache), so the stops are real.

## Phase 2 (rounds 24-25 and a confirmation): pipelines

into a D3D12 pipeline library (`host-pipelines.bin`, 1.4 MB here: on AMD the compiled code

cache" configuration is what every earlier run of the same exe had. Each start made the
2,663 pipelines of `early-pipelines.txt` (every pipeline drawn with in earlier runs) on 8

## Remaining bottlenecks

1. Physical memory: in the world the process wants ~13-14 GB private plus GPU memory on a PC
   with ~9-11 GB available; it runs only by paging (0.7 fps).
2. GPU device loss ~10 s into the world, with the card's memory at its budget.
3. The title's own memory: ~6.4 GB of mapped pages at the title screen, most of private.
4. Buffer windows (1.1-1.9 GB in the world earlier) not yet measured or reduced (task 2).

## Recommended next phase (not implemented)

- Device loss first: a diagnostics build (`VICTORY_D3D12_DEBUG=1`, DRED) of one paging-guard
  run to name the faulting command; check whether residency (`MakeResident`/`Evict`,
  `SetResidencyPriority`) or a lower texture budget (`VICTORY_TEXTURE_ROOM_PERCENT`) keeps the
  card under its budget at world entry.
- Native UMA path: read `D3D12_FEATURE_DATA_ARCHITECTURE1` (UMA, CacheCoherentUMA) and on such
  adapters put host copies the CPU fills in CPU-visible default-heap memory
  (`D3D12_HEAP_TYPE_CUSTOM`, write-back, L0) instead of an upload copy plus a card copy; skip
  "card" copies of buffers entirely (each is a second copy in the same RAM); size budgets
  from one pool (DXGI local budget = system RAM) rather than two.
- Then measure the buffer windows' really unmapped bytes in the world (the census only counts
  windows containing some unmapped page) before any window change.
- Same work applies to other AMD UMA chips (Radeon 890M, Ryzen AI Max+ 395); keep it behind
  the UMA/low-RAM detection so discrete GPUs are unaffected.
